## Цель v0.1

**Обратный расчёт ТЭП.** Пользователь задаёт площадь квартала, регион (СПб), ограничения и состав учитываемых объектов; программа подбирает максимально допустимый КИТ, при котором выполняется баланс территории и нормативные требования, и возвращает связанные ТЭП.

Прямой расчёт (`compute_tep_for_kit(kit, ...)`) — внутренняя функция, лежит под обратным режимом и переиспользуется в проверочном режиме v0.2.

## Архитектура (4 слоя)

```
configs/        — YAML: нормативы по ВРИ-кодам. Цифры живут только тут.
src/urban_model/
  normatives/   — Pydantic-схема, loader (russia↔spb наследование), resolver.
  models/       — Site, Housing, Social, DecisionVariables, TEPField, TEPResult.
  calculations/ — чистые функции без побочных эффектов. Ядро.
  core/         — forward (compute_tep_for_kit) и inverse (solve_max_kit, бисекция).
  modes/        — публичные точки входа (inverse в v0.1).
```

Принцип: расчётное ядро не знает ничего про режимы работы. Один движок — все режимы.

## Нормативы — структура

Двухуровневая система YAML: `configs/russia.yaml` (база, СП 42.13330.2016) + `configs/spb.yaml` (`parent: russia`). Регион переопределяет только то, что отличается; недостающее наследуется от базы.

**Ось организации — ВРИ-код** (Приказ N П-0412). Озеленение и парковки в ПЗЗ СПб структурированы именно так. Семантические алиасы (`kindergarten = "3.5.1"`, `housing = "2.6"`) — поверх, для удобства.

Каждый параметр имеет явный `type`:

- `scalar` — простое число (мест/1000 = 61, КИТ_max = 2.5).
- `piecewise` — кусочно-постоянная функция от аргумента (площадь участка ДОУ от вместимости; ЗНОП от КИТ).
- `conditional` — зависит от категориальной переменной (мин/макс вместимость ДОО от building_type).

Каждый параметр обязательно содержит `source` — ссылку на нормативный документ (СП, НГП, ПЗЗ, РМД, письмо). Без источника параметр не принимается — он юридически невалиден.

В коде универсальный интерфейс:

```python
norms = load_normatives(profile="spb")
plot = norms.resolve("social_objects.kindergarten.plot_area_per_place",
                     capacity=180)  # → 40 (попадает в "до .inf" ступень)
kit_max = norms.resolve("kit_limits", planning_doc="yes")  # → 2.5
```

## TEPResult — структура

Каждое поле результата — это `TEPField`, а не голое число:

```python
TEPField(
    value: float,            # принятое к расчёту значение
    normative: float | None, # нормативное (без округлений и ручных правок)
    user_value: float | None,# пользовательское (если задано вручную)
    status: Status,          # ok / warning / error / manual / no_data
    source: str | None,      # ссылка на документ
    formula: str | None,     # текст вида "население × 61 / 1000"
)
```

Это закрывает требования ТЗ: историю расчёта (§19.1), статусы показателей (§19.3), видимость ручных правок (§12), ограничивающий фактор в `solve_max_kit`.

## Принципы разработки

- **Цифры — только в YAML.** Никаких magic numbers в коде.
- **Расчёты — чистые функции.** На вход числа и нормативы, на выход — `TEPField`. Никаких побочных эффектов.
- **Источник у каждого норматива.** Без `source` параметр не принимается.
- **Pydantic для всего, что приходит извне.**
- **Регион переопределяет, не дублирует.**
- **Один движок — все режимы.** Все режимы дёргают один `compute_tep_for_kit`.
- **Расширяемость через типы, а не через ветвления.** Новый вид норматива → новый `type`. Новый ВРИ → новый ключ. Код не разрастается.
