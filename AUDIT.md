## 🚨 Главные находки smoke-теста (приоритет)

### S-1. На малых кварталах Парето даёт **0 рекомендаций** молча

| Квартал | Base feasible | Pareto feasible/total | Recs |
|---|---|---|---|
| 1 000 м² (0.1 га) | ❌ False | **0/200** | **0** |
| 5 000 м² (0.5 га) | ❌ False | **0/200** | **0** |
| 50 000 м² (5 га) | ✅ True | 153/200 | 3 |
| 200 000 м² (20 га) | ✅ True | 158/200 | 3 |

**Причина:** на квартале <5 000 м² нормативы плотности 450 чел/га + 25% озеленения квартала **физически противоречивы** (см. v0.8.7). База уже не feasible, а в Optuna все 200 trials падают по той же причине. Сейчас UI показывает «✅ Рекомендации актуальны (0/200 feasible)» — пустые карточки без объяснения.

**Действие (P1):** при `bundle.n_trials_feasible == 0` показать предупреждение типа:
> ⚠ Нет feasible-сценариев. Возможные причины:
> • Малый квартал (нормативы 25% озеленения + 450 чел/га противоречивы);
> • Слишком узкие ограничения;
> • Соцобъекты не помещаются нормативно.  
> Попробуйте: отключить норматив озеленения в Параметрах / разрешить все типы парковок / снять диапазон этажности.

### S-2. На малом квартале соцобъекты получают **5 мест ДОО, 25 СОШ** — заведомо невалидно

На 1000 м² население 2 чел → ДОО требуется 0.122 места → округление до 5 мест (multiple=5) → 1 объект 5 мест → **меньше capacity_min=120**. Тот же эффект для СОШ (25 мест < 550). Появляется WARNING с кодом `SOC_CAP_MIN_BELOW`, но пользователь видит «1 ДОО на 5 мест» как реальное значение.

**Действие (P1):** при `pop < capacity_min` для соцобъекта автоматически предлагать в UI:
> 💡 Население {pop} чел слишком мало для отдельного ДОО (минимум {capacity_min} мест). Используйте «Только потребность» (`only_demand=True`) — место рассчитывается, но объект размещается за пределами квартала.

Альтернатива: при `pop < N_threshold` автоматически устанавливать `only_demand=True` (с уведомлением).

### S-3. На большом квартале (200 000 м²) `apt` идентичен у **двух разных** рекомендаций

Smoke:
```
Site 200 000 m²:
  [Максимум площади] apt=179 992 profit=-120 447  (all open)
  [Максимум прибыли] apt=167 933 profit=-14 536   (mix)
  [Сбалансированный] apt=179 992 profit=-15 831   (open+UG)
```

«Максимум площади» и «Сбалансированный» имеют **одинаковую площадь** (179 992). Причина: при `KIT` упёртом в нормативный потолок (2.5 при ДПТ), площадь квартир — фиксированная функция от площади квартала. Разные mix парковок дают одинаковую apt при разной прибыли.

Стратификация по архетипу пытается выбрать разные парковки, но `_select_three` фильтрует по `fingerprint` (включающему архетип), не по apt. Если два варианта имеют разный архетип, но одинаковую apt — оба попадают.

**Действие (P2):** уточнить логику — например, для «Сбалансированный» предпочитать **отличный от max-apt архетип ПЛЮС не идентичный apt**. Или в UI явно отметить «KIT упёрся в нормативный потолок, площадь — максимальна» с подсказкой о других факторах.

## P1 — Высокие (12 пунктов)

### P1-1. Молчаливое `except Exception: continue` в сканах

📍 `src/urban_model/optimize/scans.py:174-176, 230-233, 295-298`

Любое исключение в `solve_max_kit()` → точка пропадает из графика без следа. На графике могут быть пропуски, но пользователь не понимает почему. Если 5 из 11 точек упали — пользователь видит 6 точек.

**Фикс:** ловить только `(ValueError, KeyError, RuntimeError)`, остальное — наружу. Логировать через `logging.warning` с указанием параметра. Можно добавить `ScanPoint.error: str | None` и помечать «упало» точки на графике.

### P1-2. Пороги `_has_token_parking` (50/30) hardcoded — не масштабируются

📍 `src/urban_model/optimize/pareto.py:97-103`

`_MIN_ML_PLACES=50`, `_MIN_UG_PLACES=30`. На квартале 200 000 м² где требуется 2000 м/м, 49 ML — это 2.5% и логично отфильтровать. На квартале 5 000 м² где всего 25 м/м, требование «не меньше 30 подземных» означает что подземные вообще запрещены (а это нерыночное ограничение для застройщика среднего масштаба).

**Фикс:** сделать пороги **относительными** к `total_required`: `min_ml = max(50, total*0.05)`. Или вынести в `ParetoConstraints` как поля `min_ml_places` / `min_ug_places`.

### P1-3. Граничные условия фильтра гибридов парковок

📍 `src/urban_model/optimize/pareto.py:87`

`_is_hybrid_parking(threshold=0.10)` использует `ml > threshold and ug > threshold`. Ровно 10% оба → НЕ гибрид (не фильтруется). 10.1% оба → гибрид. Скачок на границе. Лучше `≥`.

**Фикс:** изменить `>` на `>=` в `_is_hybrid_parking`. Документировать порог как «10% включительно».

---

### P1-4. Архетип `_parking_archetype` — точная граница на 60%

📍 `src/urban_model/optimize/pareto.py:217-224`

`if ug >= 0.60` — точное условие. Вариант `ug=0.5999` попадает в `custom_surface`, `ug=0.6000` — в `custom_deep_underground`. Нестабильность стратификации при шуме TPE-сэмплера. Лучше — **гистерезис** (вход 0.55, выход 0.65) или плавная классификация.

**Фикс:** добавить тест на граничные значения. Если расхождение классификации критично — ввести два порога (вход/выход).

### P1-5. Карточка с парковками 0/0/0 при `parking_mode="min_open"`

📍 `src/urban_model/ui/optimizer.py:399` (`_rec_options_from_params`)

Для `parking_mode != "custom"` создаётся `ParkingConfig(mode=mode)` с **дефолтами** open=0.125, ug=0.875, ml=0 (берётся из `ParkingConfig` schema). Но `multilevel_levels` / `underground_levels` из `base_options` теряются. KPI-блок покажет дефолты, а не фактические уровни сценария.

**Фикс:** передать `multilevel_levels` и `underground_levels` даже для `mode != "custom"`. Также — в `_extract_kpi_fields` показывать сами **уровни** (МУ-этажность, UG-уровни), а не только число мест.

### P1-6. Парковки ВПП — единый коэф 64 м²/м.м. **рассогласован** с реальностью

📍 `configs/spb.yaml` секция `parking.vpp.m2_per_place=64`

Например, медицина (ВРИ 3.4.1) — норматив требует **существенно больше** парковки чем 1.56 м/м на 100 м² (текущее усреднение). По реальным проектам — медцентр на 26 посещ/смену требует ~10-15 мест парковки, а текущая формула даёт 3 места. 4-кратный разрыв.

**Фикс:** вернуть piecewise-таблицу `m2_per_place` по ВРИ (была в v0.7.0–v0.7.1 до упрощения). Это даст точные парковки для смешанных кварталов.
